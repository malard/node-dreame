# node-dreame v0.2 Plan

Drafted 2026-05-07; major revision after reading wealth-monitor's
integration gap report at
`C:\Development\wealth monitor\docs\dreame-integration-gaps-2026-05-07.md`
(written same day against `node-dreame@0.1.5` from the consumer side).

That doc supersedes my earlier read of the situation. Two findings
in particular reshape the plan:

- **`tail.rism` IS the saved-map blob, embedded as a base64 envelope
  inside every live I-frame.** Decode it recursively and you get a
  `MapData` whose tail has `vw`/`vws` at top level. So the fix to
  surface user geometry on the live channel is purely local to
  `MapDecoder.decode` — no eager OSS-pointer fetch on bootstrap,
  no `MapManager` changes for B1.
- **Wealth-monitor already ships an OSS-pointer caching pattern**
  that bypasses every cloud HTTP path for saved-map fetches. Pure
  memoise of the most recent PATH/POINTER_JSON push + a direct
  `OssFetcher.fetchBlob` call. This obsoletes plan-§C4's "MITM
  capture of `getOss1dDownloadUrl`" — we don't need a different
  endpoint, we need to cache the pointer we already see on every
  PATH push.

## Scope

### A. Decoder gaps

A1. **Recurse into `tail.rism`.** In `MapDecoder.decode`, after
parsing the outer tail, if `tail.rism` is a non-empty string, decode
it as a nested map envelope and **merge the inner geometry into the
outer `MapData`**. Specifically merge: `virtualWalls`,
`restrictedAreas`, and any new fields added by A2/A3 below. Don't
merge live state (path, robot pose, segments, layers) — outer wins
for those. This makes the consumer contract uniform: `MapData.virtual
Walls` is "all walls for this floor" regardless of where they're
physically stored.

**Test:** `test/map/decoder.rism-recurse.test.ts` against the saved
fixture (decode the saved-map blob as outer; assert inner tail's
`vw`/`vws` arrive on the outer `MapData`).

A2. **`vw` block — extend extraction.** Current
`parseVirtualWalls` reads `line`/`rect`/`mop`. Add:

- `vw.nocpt` → `restrictedAreas` with `kind: "noGo"` (4-int rect,
  same shape as `vw.rect`). Wealth-monitor verified one entry on
  r2532a 2026-05-07.
- `vw.cliff` → TBD; parse defensively (if non-empty, treat as line
  segments per Tasshack `map.py:4699`). Empty on r2532a today.
- `vw.addcpt` is **carpets, not walls** — parse separately (see A4).

A3. **`vws` block — entirely new.** Per Tasshack `map.py:4678-4691`:

- `vws.vwsl` → `virtualWalls`. Wealth-monitor verified 3 entries on
  r2532a. When `vws.npthrsd` is also present in the same tail, these
  are *passable* thresholds; when absent, they're plain virtual
  thresholds. Surface via the new discriminator below.
- `vws.npthrsd` → `virtualWalls` with `kind: "threshold"`. Wealth-
  monitor verified 2 entries on r2532a.
- `vws.ramp` → `ramps: readonly MapRamp[]` (empty on r2532a).
- `vws.cliff` → as A2.cliff (defensive parse).

**Discriminator on `MapVirtualWall`** (per wealth-monitor's
suggestion): `kind?: "wall" | "threshold"` (default `"wall"` when
absent). Additive, doesn't break callers.

A4. **`vw.addcpt` / carpet polygons.** Wealth-monitor surfaced these
as a distinct concept (added-carpet rectangles with segment id and
shape codes 8..12, up to 13 fields). Surface as:

- `addedCarpets: readonly MapCarpetArea[]`

`vw.addcpt` is the user-added variant. Whether there's a paired
"removed-carpet" or not is unclear — look at Tasshack's `parseCarpets`
and surface symmetrically if so. (My earlier read called this
"removedCarpets" — wealth-monitor's read is "added carpet zones the
user marked". Reconcile by reading the Tasshack source again before
naming.)

A5. **`sneak_areas` / `sneak_areas_end`.** Per Tasshack
`map.py:4776-4809`, polygon shape — `{ id, type, hide, roi: [n*2
ints], ms?, area? }`. Surface as `lowLyingAreas: readonly
MapPolygon[]`. Prefer `sneak_areas_end` when both are present
(richer; carries `area`).

A6. **`walls_info` surfacing.** Per-room wall geometry. Keep types
strict — `storeys[].rooms[].walls[]` with `{ type, beg_pt_x,
beg_pt_y, end_pt_x, end_pt_y, normal_x, normal_y }`.

A7. **Fix `parsePathTr` line-delta accumulation bug** (verified by
wealth-monitor 2026-05-07). `line`-type ops in the `tr` string carry
**relative deltas** to the preceding `sweep`/`sweep-and-mop`/`mop`
absolute waypoint, NOT absolute coords. Today the parser emits the
deltas as literal points, which renders all line traces as a tight
cluster around `(0,0)`. Fix: accumulate deltas against the rolling
anchor (preceding sweep waypoint, then previous point within the
same line).

**Algorithm** (from wealth-monitor's `unwindLinePaths`):
```
let anchor = null;
for (const p of paths) {
  if (p.type === "sweep" || p.type === "sweep-and-mop" || p.type === "mop") {
    anchor = p.points[0];
  } else if (p.type === "line") {
    let cx = anchor.x, cy = anchor.y;
    const abs = [{ x: cx, y: cy }];
    for (const d of p.points) {
      cx += d.x; cy += d.y;
      abs.push({ x: cx, y: cy });
    }
    p.points = abs;
    anchor = { x: cx, y: cy };
  }
}
```

This is a pure decoder bug, not an API change — fix it in
`parsePathTr` (or its callers in merge.ts) so the surfaced `points`
are always absolute world-frame mm.

**Test:** wealth-monitor verified the result lands inside the map
bounds; replicate as a fixture-driven test asserting the same.

A8. **Doc the `MapData.rotation` convention.** Wealth-monitor
applied `ctx.rotate(rotation * π / 180)` after a Y-flip and got the
mirrored orientation. The d.ts is silent on:

1. Clockwise or counter-clockwise.
2. Apply before or after Y-flip.
3. Whether the value is "the rotation the device thinks the map is
   at" or "the rotation the renderer should apply to display it like
   the app does".

Resolve and document. Pick the convention that makes the obvious
canvas transform (Y-flip then rotate) match the Dreamehome app — if
that means flipping the sign of the surfaced value, do it (call out
in CHANGELOG; this is a v0.2 since rotation was already shipped).

A9. **JSDoc cleanups for empty-vs-null and pre-decoded names.**
Wealth-monitor flagged:

- `MapSegment.name` is already base64-decoded; doc could spell out
  "use as-is, do not double-decode" to head off the ambiguity.
- For unnamed segments, `name === ""` (empty string) on r2532a —
  not `null`. Worth a JSDoc note on that empty-string convention so
  consumers don't write `s.name === null ? … : s.name`.

A10. **Fix `docs/live-map-format.md:186` inaccuracy.** The line
claims `sneak_areas` "format same as `vw.rect`". It isn't — see A5.

### B. Live-I-frame geometry — fold into the existing path

B1. **`vacuum.map.on("map", …)` carries geometry post-A1.** Once the
decoder recurses into `tail.rism`, the existing `MapManager` path
emits `MapData` with `virtualWalls`/`restrictedAreas`/etc. populated
on every I-frame — no new event surface, no eager bootstrap fetch.
The `vacuum.map.geometry` getter idea from the earlier draft is
unnecessary.

B2. **`mapInfo` event already wired** (`mqtt.ts:338-349`,
`vacuum.ts:362`). No work needed.

### C. OSS-pointer caching (the only cloud-path item that survives review)

C1. **`Vacuum.rememberOssPointer()` + `Vacuum.fetchMapFromOss()`**
(per wealth-monitor's suggested API). Cache the most recent
`siid 6 piid 3` (PATH) and `siid 6 piid 8` (POINTER_JSON) pushes;
expose a method that resolves them via `OssFetcher.fetchBlob` +
`MapDecoder.decode` without any HTTP round-trip to the device.
Persistence is the consumer's job — accept an injected
`pointerStore: { read, write }` so the lib stays IO-free.

This is the missing path on idle/sleeping devices. Wealth-monitor
shipped a private version that's been working since 2026-05-06;
folding it into the lib means future consumers don't have to
re-implement.

```ts
class Vacuum {
  rememberOssPointer(opts?: {
    pointerStore?: {
      read(): OssPointer | null;
      write(p: OssPointer): void;
    };
  }): void;

  fetchMapFromOss(opts?: { filename?: string }): Promise<MapData>;
}
```

This obsoletes the earlier `getOss1dDownloadUrl` MITM-capture item —
we don't need a different OSS endpoint, just memoise the pointer we
already see on every PATH push.

**Earlier C2/C3/C4 dropped after re-reading the 0.1.5 code:**
- `refresh()` already preserves `state.online` on 80001
  (`vacuum.ts:288-321`).
- `ActionResult { kind: "acked" | "no-ack" }` already shipped
  (`vacuum.ts:97-99`); reads still throw, writes return the
  discriminated result.
- `vacuum.state` MQTT-only seeding wasn't flagged by wealth-monitor
  as a blocker — `getDevices()` snapshot + MQTT pushes appear to
  cover the consumer's needs in practice. Hold this open as a future
  item only if a real consumer hits it.

## Non-goals for v0.2

- Multi-floor map manager.
- VSLAM pixel-decode path (variant C).
- `OLD_MAP_DATA` decoding.
- P-frame AES IV table (wealth-monitor flagged it as a separate gap;
  needs per-model IV capture).
- Editing geometry via the lib (write path).

## Suggested order

1. **A7** — `parsePathTr` line-delta bug. Pure decoder fix; landing
   it first means future test fixtures display correct paths.
2. **A8** — settle the `rotation` convention. Affects every
   downstream renderer; nail it before more A-items rebase on it.
3. **A1** — `tail.rism` recursion in `MapDecoder.decode`. The
   single biggest unblocker for consumers.
4. **A2, A3** — extend `parseVirtualWalls` + add `vws` parsing,
   add the `kind: "threshold"` discriminator on `MapVirtualWall`.
5. **A4, A5, A6** — carpet polygons, low-lying areas, walls_info.
6. **A9, A10, D5** — JSDoc + doc cleanups.
7. **C1** — `rememberOssPointer` / `fetchMapFromOss`. Larger API
   addition; can ship after the decoder gap is closed.
8. **D1, D4** — hygiene + empty-state fixture, any time.

## Breaking-change inventory

- A1 (rism recursion): consumers that today read `MapData.virtualWalls`
  see populated arrays where they used to be empty. **Behavioural
  change**, not a type break. CHANGELOG note; arguably a bug fix.
- A3 `MapVirtualWall { kind?: "wall" | "threshold" }`: additive.
  Default `"wall"` so existing checks don't break.
- A4-A6: new optional fields on `MapData`. Additive.
- A7 (`line`-delta accumulation): consumers that worked around the
  bug locally (like wealth-monitor) will now double-accumulate. Call
  out in CHANGELOG so they can drop their workaround.
- A8 (rotation convention): if the surfaced value's sign flips, this
  is observable in every renderer that applies `rotation`. Worth
  hedging — could ship a new `displayRotation` field with the
  guaranteed convention and deprecate `rotation` to keep back-compat.
- C1 (`rememberOssPointer` / `fetchMapFromOss`): additive APIs.

Net: minor bump (v0.2) primarily because of A1 (geometry-now-populates),
A7 (path-deltas-now-correct), and possibly A8 (rotation sign).
